这个漏洞是自查发现的，出现在我们自己写的代码里，影响的是"AI 指令确认"这条链路。

结论先说：当时任何登录用户，只要拿到另一个用户待确认指令的令牌，就能替对方确认并落库。 修复是一行代码，但根因值得写下来——它是一个非常典型的"安全校验依赖了一个约定存在、而实际为 undefined 的字段"。

一、背景：什么是"一次性确认令牌"

我们的 AI 记账流程是这样的：

  1. 用户说一句"陈晓报销打车费 128，现金"；
  2. 模型解析成结构化参数，服务端预演出一张确认卡片（不落库）；
  3. 服务端签发一个一次性令牌，绑定：当前用户 + 当前账套 + 卡片载荷哈希；
  4. 用户点"确认执行"，前端带着令牌提交；
  5. 服务端校验令牌归属 → 执行 → 落草稿。

第 5 步的校验代码长这样：

ts
require(token: string, companyId: string, userId: string): TokenPayload {
  const found = this.entries.get(String(token ?? ''))
  if (!found) throw new BadRequestException('指令已失效，请重新说一遍')
  if (found.expiresAt < Date.now()) throw new BadRequestException('指令已超过 15 分钟，请重新说一遍再确认')
  if (found.companyId !== companyId) throw new BadRequestException('该指令不属于当前账套，已拒绝执行')
  if (found.userId !== userId) throw new BadRequestException('该指令由其他用户发起，不能代为确认')
  return found
}

逻辑看起来没问题：令牌里存了 userId，调用时传进来当前用户 userId，不等就拒。

控制器里传的是：

ts
const user = getCurrentUser(req)   // 来自 JWT 守卫
const payload = this.tokenStore.require(body.token, companyId, user.id)

问题就出在这个 user.id。

二、根因：user.id 一直是 undefined

我们的认证用的是 passport-jwt。它的默认行为是：把解码后的 JWT 载荷原样挂到 request.user 上，不做任何字段映射。

我们的 JwtStrategy 当时是这么写的：

ts
// 修复前
validate(payload: JwtPayload): CurrentUser {
  return payload
}

而我们的 JWT 载荷里，用户 ID 存在 sub 里（JWT 标准的 subject）：

json
{ "sub": "4f19ee5b-e4f8-45f5-9ee8-5fa4b43d93a1", "username": "admin", "companyId": "..." }

载荷里没有 id 字段。

于是 user.id 恒为 undefined。而业务代码里到处都在用 user.id：审计日志的操作人、数据隔离、令牌归属校验。

那么第 5 步的校验实际发生了什么？

ts
found.userId  // → undefined（签发时也是从 user.id 拿的！）
userId        // → undefined
undefined !== undefined  // → false，不抛错

签发的时候也是 undefined，校验的时候也是 undefined，两边相等，校验通过。

这是最坏的一种失效：不是"拒绝了所有人"，也不是"崩溃报错"，而是安静地永远通过。看起来一切正常，功能好用，测试全绿。

三、为什么测试没抓到

诚实复盘，三个原因：

1）所有测试用的是同一个账号。

我们写了一批端到端脚本验证 AI 五类动作，全部用 admin 登录。同一个人签发、同一个人确认，undefined !== undefined 也是 false，通过。功能完全正常。

2）没有"跨身份"用例。

"换个用户提交别人的指令应该被拒绝"——这条用例当时不存在。而它恰好是唯一能暴露问题的用例。

3）没有任何地方断言"用户身份必须完整"。

如果有个中间件在入口就检查 user.id 是否存在，这个 bug 第一时间就会被发现（因为每个请求都会 500）。但我们没有——我们假设 JWT 守卫通过 = 身份完整。

四、修复

第一处，一行：

ts
// 修复后
validate(payload: JwtPayload): CurrentUser {
  return { ...payload, id: payload.sub }   // 显式由 sub 派生 id
}

sub 原样保留（建账等其他入口还在用它），同时补上 id。

第二处，把"身份可能为空"从类型上堵住 —— 以及它为什么没堵住：

JwtPayload.sub 与 CurrentUser.id 现在都声明成必填 string，"身份字段可能缺失"这件事在业务侧应该是不成立的。但必须诚实补一句：项目的 strictNullChecks 目前是关着的（backend/tsconfig.json）。开关关着的时候，把一个没有 id 的对象赋给 CurrentUser，TypeScript 一声不响。

所以类型在这里只是"约定"，不是"保证"。打开 strictNullChecks 已经列进重构清单——这类 bug 想靠编译器兜住，得先有那个开关。

第三处，补跨身份用例：

ts
// A 签发、B 提交 —— 端到端脚本里的关键断言
const plan = await planAs(userA, '记一笔 800 元的水电费')
const res  = await commitAs(userB, plan.token)
assert(res.status === 400)                              // 修复前是 200
assert(res.body.message.includes('不能代为确认'))

同样诚实说：仓库现在没有引入单元测试框架，这批端到端验证是独立脚本，跑完不留痕。但这条用例本身是验证过的——把 jwt.strategy.ts 里的 id: payload.sub 改回 return payload，它立刻变红。把它固化进 CI 是待办，不是已完成。

五、影响面评估

修完要回答一个问题：这个 bug 还影响哪里？

我们顺着 user.id 全量扫了一遍，受影响的只有三处：

位置影响严重程度
一次性令牌归属校验可替他人确认指令高（本漏洞）
审计日志操作人记录为 null中（可追溯性受损）
数据隔离（按用户过滤账套）若依赖 user.id 会失效需逐处确认

第三条最值得警惕。我们的账套隔离主要走 companyId（也来自 JWT 载荷，字段名对得上，没受影响），但只要有任何一个查询用 user.id 做过滤，那一处就是越权读。逐处确认后，没有发现越权读路径。

没有发现被利用的痕迹：审计表里那段时间没有异常的「操作人为空」的跨账号提交记录（user_id / user_name 同时为空的行）。这个漏洞从引入到修复都存在于本地开发分支，两个公开版本都不含这条链路——版本层面的核对写在第六节。

六、影响版本范围与 CVSS 自评

6.1 哪些版本受影响

版本是否含「AI 指令确认」链路可利用性
v1.0.0（2026-10-23）否不可利用
v1.1.0（2026-11-13）否（后端尚无 AI 内核模块）不可利用
本地开发分支，2026-11-11 → 11-15是可利用（仅自用环境）
801381f 及之后是（已修复）不可利用

两个公开版本都能自己查：git show v1.1.0:backend/src/modules/auth/jwt.strategy.ts 里确实是 return payload——但 git ls-tree --name-only v1.1.0:backend/src/modules 也能看到，那一版后端只有 accounts / books / closing / vouchers 等十来个模块，没有 AI 指令确认链路，token.store.ts 根本不在里面。

没有令牌，就没有「替别人确认」这条路。 缺陷随 AI 记账功能进入本地分支，随 801381f 一起修掉，没有进过任何带该功能的发布包。

6.2 CVSS 3.1 自评

向量：CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:L/A:N → 4.3（Medium）

逐项理由（自己给自己打分，就得把理由摆出来让人反驳）：

指标取值理由
AVN（网络）走 HTTP API，不需要物理接触或同一局域网
ACL（容易）拿到令牌即可，无竞态、无特殊配置、无需猜参数
PRL（低权限）需要先登录（任意普通账号），不是匿名可利用
UIN（无需交互）受害者点不点那张卡片无所谓，攻击者直接 POST 提交
SU（范围不变）影响局限在本应用内，不波及宿主或下游系统
CN（无泄露）令牌不携带业务数据，越权确认也读不到他人账目
IL（低完整性影响）只能写草稿，草稿要人工审核才入账，账实不符的最终风险有限
AN（无可用性影响）不删除、不锁定、不消耗资源

为什么不是更高。 如果这套系统存在「自动审核」开关，I 会升到 H，总分变 6.9。我们没有这个开关——AI 的落地动作只有 draft / list / archive，没有 direct，这是草稿闸门的另一面价值：它把越权写入的爆炸半径压到了「一堆待审草稿」。

为什么不是更低。 PR 不能取 H：确实只要一个普通登录账号；AC 不能取 H：不需要口令、不需要会话固定、不需要任何前置条件。

Temporal / Environmental 不评。 没有公开利用代码，也没有因部署环境不同而产生的缓解差异，评了只是自己给自己加分。

最后强调一次：这是自评，不是 CNA 或第三方评估。有不同意见，欢迎照上面这张表逐项反驳。

七、四条教训

1）安全校验必须 fail-closed，不能靠"字段应该存在"。

if (a !== b) throw 这种写法，前提是 a、b 都是有效值。只要有一边可能是 undefined，这个校验就等于没有。正确姿势是先断言再比较：

ts
if (!user?.id) throw new UnauthorizedException('身份信息不完整')   // 先断言
if (found.userId !== user.id) throw new BadRequestException(...)   // 再比较

2）"永远通过"比"永远失败"危险得多。

永远失败会被立刻发现（功能不能用）；永远通过会活到线上。所以做安全校验时，我会刻意想一个问题：这个判断在什么输入下会静默通过？ 然后为那个输入写用例。

3）跨身份用例是必测项。

凡是涉及"归属"的逻辑——资源属于谁、令牌属于谁、数据属于哪个租户——必须有"换个身份来访问"的用例。同账号测试再多也覆盖不到这类问题。

4）异常信号别放过。

当时如果注意到"审计日志里操作人一栏经常是空的"，可能会更早发现。空值、默认值、null 展示——这些"看起来无害的小问题"经常是更严重问题的影子。

八、为什么把这件事写出来

有人劝我别写：一个已经修好的、没被利用的漏洞，公开出去只会让人怀疑产品。

我不这么看，两个理由：

第一，这是可验证的坦诚。 我在 README 和官网都在说"AI 改不了账、令牌绑人绑载荷"。如果连自己修过什么漏洞都不敢写，那些声明就只是文案。修复的那行代码在公开仓库里，jwt.strategy.ts 的注释就写着这段来历，谁都能查——包括查我上面哪句话写大了。

第二，这类 bug 太常见了。 passport-jwt 不补 id 这件事，我在搜资料时看到过不止一个人踩。写出来至少能让人在自己项目里 grep 一下 user.id。

顺便说一句，这也是我们坚持"安全靠代码不靠文案"的原因：任何安全声明都应该能对应到一段可执行、可测试的代码，否则就是营销。

九、给自己留的三条自检清单

贴在 issue 里，每次改认证相关代码时过一遍：

  1. JWT 载荷里的每一个字段，业务侧用的是不是同一个名字？ 不一致就显式映射，别依赖侥幸。
  2. 所有"归属校验"是否都有跨身份用例？
  3. 审计字段出现空值，是不是有更深的原因？
